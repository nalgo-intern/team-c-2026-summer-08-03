# 開発メモ（実装して分かったこと）

機械学習パート（画像認識・レシピ推薦）の実装中に判明した知見をまとめる。
**「仕様書に反映すべきこと」の節は、そのまま仕様書・最終レポートの修正箇所**になる。

## 1. 画像認識（CLIP）

### 1-1. `en_label` は単語ではなく「説明句」にする必要がある

これが今回いちばん効果の大きかった発見。

`ingredients.csv` の豆腐まわりの `en_label` は当初こうなっていた。

```
豆腐      → tofu
高野豆腐   → dried tofu
厚揚げ     → thick fried tofu
油揚げ     → fried tofu pouch
```

**4つすべてが "tofu" を含み、正解であるべき「豆腐」がいちばん情報量が少ない。** CLIP から見ると豆腐の写真は4つ全部に似ていて、視覚的特徴を多く書いてあるラベルの方が高スコアになってしまう。

競合ラベルと区別できる軸を言語化して解決した。

```
豆腐 → a block of plain white tofu
```

- `plain`（加工していない）→ 高野豆腐・厚揚げとの対比
- `white`（白い）→ 高野豆腐の茶色との対比
- `block`（塊）→ 油揚げの薄い形状との対比

**結果: 豆腐の Top-1 正解率 40% → 100%、全体 Top-1 78% → 84%（目標80%を突破）。**

### 1-2. 粒度が細かすぎる食材群が誤認識の主因

`ingredients.csv` には視覚的に区別できない食材が別々の行として並んでいる。

| 食材群 | 中身 | 影響 |
|---|---|---|
| 豆腐系 | 豆腐 / 高野豆腐 / 油揚げ / 厚揚げ | en_label の改善で解決済み |
| トマト系 | トマト / ミニトマト / ホールトマト缶 | トマトが 60% に留まる原因 |
| 鶏肉 | 鶏もも肉 / 鶏むね肉 / 鶏ひき肉 / 鶏手羽元 | 後述（推薦側にも波及） |

写真からもも肉とむね肉を見分けるのは人間でも難しく、モデルの問題ではなくラベル設計の問題。

### 1-3. 「鶏肉」がラベルとして存在しない

仕様書の評価対象10種類には「鶏肉」があるが、`ingredients.csv` に「鶏肉」という行は無い（上記4部位のみ）。**このままだと `recognize()` が「鶏肉」を返すことは構造的に不可能**で、評価すると必ず0%になる。

`evaluate.py` に `ALIASES` を用意し、「鶏肉」フォルダの画像はどの部位を答えても正解とみなすようにした。

```python
ALIASES = {"鶏肉": {"鶏もも肉", "鶏むね肉", "鶏ひき肉", "鶏手羽元"}}
```

**測定方法を変えた以上、レポートに明記が必要。** 仕様書の評価対象は「鶏肉」というカテゴリなので、部位を区別しないのは仕様に忠実な解釈だが、黙ってやると評価の信頼性を疑われる。

なお、トマト → ミニトマトの誤認識も同じ方法で「正解」にできるが、**これはやらなかった**。鶏肉はラベル自体が存在しないための構造的対処だが、トマトは正しいラベルが存在していてモデルが2位に置いただけなので、エイリアスを足すのは単なる指標の水増しになる。

### 1-4. 最終的な評価結果（50枚 / 10種類）

```
食材        枚数   Top-1   Top-3
--------------------------------
じゃがいも      5     80%    100%
なす         5    100%    100%
にんじん       5    100%    100%
キャベツ       5     60%    100%
トマト        5     60%    100%
ピーマン       5    100%    100%
卵          5    100%    100%
玉ねぎ        5     60%    100%
豆腐         5    100%    100%
鶏肉         5     80%    100%
--------------------------------

全体 Top-1:  84.0%  (目標 80%)  OK
全体 Top-3: 100.0%  (目標 95%)  OK
```

**3指標すべて達成。** ただし食材ごとの正解率はキャベツ・トマト・玉ねぎが**ちょうど60%**で目標ラインに張り付いており、余裕がない。1食材5枚なので**1枚外れると40%に落ちて目標を割る**。

### 1-5. 評価データの粒度が粗い（5枚/食材）

1枚の当たり外れが食材ごとの正解率を **20ポイント** 動かす。「60%」と「80%」の差は画像1枚。この粒度で細かい優劣を判断しても意味がないので、プロンプト調整は「なぜ効くか説明できる変更」だけを採用し、目標を満たしたら打ち切る方針を取った。

### 1-6. PNG → JPG 変換で測定値が変わる

評価画像を PNG（48.2MB）から JPG（5.9MB / 88%削減）に変換したところ、**Top-3 が 100% → 98% に低下**した。`豆腐/1` が3位から4位に落ちたため。

品質を上げても直らなかった。

```
PNG(元)   1151KB  豆腐の順位=3
JPG q90    164KB  豆腐の順位=4
JPG q95    249KB  豆腐の順位=4
JPG q100   480KB  豆腐の順位=4
```

圧縮の粗さではなく、**この画像がもともと3位と4位の境界上にあり、わずかな変化でひっくり返る**ということ。

その後 1-1 の `en_label` 改善で `豆腐/1` は1位になったため、現在この問題は顕在化していない。ただし**評価用データを加工すると測定結果が変わりうる**という教訓は残る。

### 1-7. 実装上の罠: transformers v5 の API 変更

`get_text_features()` / `get_image_features()` は、v4 まではテンソルを直接返していたが、**v5 では `BaseModelOutputWithPooling` というオブジェクトを返す**。

```python
# v4 の書き方（v5 では .norm() が無いと言われて落ちる）
features = model.get_text_features(**inputs)

# v5
features = model.get_text_features(**inputs).pooler_output
```

この環境は transformers 5.14.1。

### 1-8. 「認識できませんでした」の閾値（未確定）

仕様書テスト項目7のための調査。食材50枚と、食材でない画像（ノイズ・単色・文字画像などの合成6枚）でスコア分布を比較した。

| 指標 | 食材の最小 | 非食材の最大 | 判定 |
|---|---|---|---|
| **生のコサイン類似度** | 0.2871 | 0.2744 | **分離可能** |
| softmax確率 | 0.3398 | 0.3568 | 重なる |
| 1位と2位の差 | 0.0003 | 0.0146 | 重なる |

- **softmax が使えない理由**: 101候補の中の相対比較なので、非食材でも「候補の中で一番マシなもの」に確率が集まる
- **1位と2位の差が使えない理由**: トマト対ミニトマトのように、食材側でも1位2位がほぼ同点になるケースがある

**併用を推奨する第2の手法**として、「人物の写真」「ペットの写真」などのダミーラベルを候補に混ぜて、それが1位なら棄却する方式も検証した。**食材50枚を1枚も誤って弾かず**、合成非食材5枚のうち3枚を弾けた（ノイズと単色は取りこぼす）。

| 手法 | 得意 | 苦手 |
|---|---|---|
| ダミーラベル | 人物・ペット・文字など意味のある非食材 | ノイズ・単色 |
| コサイン類似度の閾値 | ノイズ・単色など低信頼な入力 | 意味のある非食材 |

**未完了: 非食材のテストデータが合成画像しかない。** 仕様書のテスト項目7が想定しているのは人物・ペット・風景といった普通の写真で、それらは CLIP が何らかの食材との類似性を見つけるためスコアが高く出るはず。食材の最小値との差はわずか 0.0127 しかないので、**現実的な非食材画像を入れたら分離できなくなる可能性が高い**。

閾値を決める際の方針: **このアプリでは誤って弾く方が明確に悪い。** 誤って弾くとユーザーは何もできず詰まるが、誤って通しても上位3候補から選ぶ仕様なので手入力に切り替えられる。迷ったら閾値は低めに。

## 2. レシピ推薦（TF-IDF）

### 2-1. TF-IDF は主役ではない

仕様書の「合致率を第1優先、類似度を第2優先」という指定により、**並び順を決めているのはほぼ合致率**で、TF-IDF は同点時の決着係。実装順序としても合致率を先に作る方が早く動くものが見える。

実測例（`鶏もも肉, 卵, 玉ねぎ` で検索）:

```
   合致率     類似度  料理名
  100%   0.727  鶏の照り焼き            不足=[]
  100%   0.489  だし巻き卵              不足=[]
   67%   0.451  ミートボールの甘酢あん      不足=['豚ひき肉']
   67%   0.451  メンチカツ              不足=['合いびき肉']
   60%   0.819  親子丼                 不足=['ご飯', 'ねぎ']
```

親子丼は類似度0.819で全体最高だが、合致率60%なので100%のレシピより下に来る。優先順位が正しく効いている。

### 2-2. TF-IDF のトークナイザは自分で指定する必要がある

`TfidfVectorizer` は英語のように空白で単語が区切られている前提。日本語かつセミコロン区切りのデータをそのまま渡すと意図しない分割になる。

食材リストがすでに Python のリストなら、恒等関数を渡すのが最も単純。

```python
TfidfVectorizer(analyzer=lambda items: items)
```

これで「食材1つ＝1トークン」が保証される。**語彙数が 101（調味料を除いた食材数）になることが検証ポイント。**

### 2-3. `TfidfVectorizer` は既定で L2 正規化する

そのため**内積を取るだけでコサイン類似度になる**。自前で正規化する必要はない（CLIP の実装と同じ構造）。

### 2-4. 主材料が少ないレシピが構造的に上位に来る

`鶏の照り焼き` の主材料は `['鶏もも肉']` の1つだけ（残りは全部調味料）。つまり**鶏もも肉を1つ持っているだけで合致率100%**になる。

判定自体は正しい（実際に作れる）が、合致率を第1優先にする以上、**材料が少ないシンプルな料理が構造的に上位を占める**。10種類の食材を持つユーザーに、8種類を使う凝った料理ではなく1材料の料理が並ぶ。

仕様どおりの挙動なので変更していないが、気になる場合は「合致した主材料の絶対数」を第3のソートキーに加える手がある（仕様から外れるので要相談）。

### 2-5. 鶏肉の粒度問題が推薦側にも波及する

レシピ側の食材は `鶏もも肉` のように部位まで指定されている。一方、画像認識が返すのも部位単位で、**写真次第でもも肉かむね肉かが変わる**。

ユーザーが「鶏むね肉」と認識された状態で親子丼（鶏もも肉が必要）を探しても合致率に加算されない。**合致率が想定より低く出たらこれを疑う。**

### 2-6. 合致率の閾値は 0.5

仕様書テスト項目6のための閾値。実測して決めた。

| クエリ | 閾値0.3 | **0.5** | 0.7 |
|---|---|---|---|
| 鶏もも肉,卵,玉ねぎ | 30件 | **20件** | 2件 |
| 卵のみ | 11件 | **7件** | 1件 |
| 豆腐,ねぎ | 19件 | **7件** | 0件 |
| 豚バラ肉,キャベツ,にんじん,じゃがいも,玉ねぎ | 28件 | **11件** | 1件 |

0.5 なら上位5件を埋めるのに十分な数が残り、かつ「主材料の半分以上が手元にある」という説明しやすい基準になる。0.7 まで上げると0件になる入力が出てしまう。

### 2-7. データの健全性（確認済み）

- `recipes.csv` 150件、`ingredients.csv` 135件（調味料34 / 主材料101）
- **主材料が0件のレシピは無い** → 合致率の分母が0になる心配は不要
- `recipes.csv` の食材はすべて `ingredients.csv` に存在（未登録0件）
- `ingredients` と `amounts` の要素数はすべてのレシピで一致
- 画像ファイルは150件すべて存在
- `aliases` 列に空欄なし、別食材への衝突なし（辞書は403キー）

## 3. Streamlit の実装上の罠

### 3-1. 操作のたびにスクリプト全体が再実行される

すべての設計がこれに影響を受ける。

- 普通のリストに `append` しても再実行で消える → `st.session_state` を使う
- `recognize()` が毎回呼ばれる → `@st.cache_data` でキャッシュ（引数は `bytes` にする。`UploadedFile` はハッシュ不可）
- モデルの再読み込みは起きない（`import` 済みモジュールは保持されるため、`recognize.py` 側の遅延キャッシュが効く）

### 3-2. ファイルの読み取り位置

`st.image(uploaded_file)` で表示すると読み取り位置が末尾に進み、その後 `Image.open(uploaded_file)` すると失敗する。

**最初に `uploaded_file.getvalue()` で bytes を取り出して使い回す。** `st.image()` も `Image.open()` も bytes を受け取れるうえ、キャッシュのキーにも使える。

### 3-3. ウィジェット生成後に session_state を書き換えられない

入力欄をクリアしようとして落ちる。

```python
text = st.text_input("食材", key="ing_text")
...
st.session_state.ing_text = ""
# → StreamlitAPIException: `st.session_state.ing_text` cannot be modified
#    after the widget with key `ing_text` is instantiated.
```

**対策: `st.form(clear_on_submit=True)` を使う。** Enter で送信できる利点もある。

### 3-4. ループ内のウィジェットの `key` は `file_id` を使う

同じ key が2回出ると `StreamlitDuplicateElementKey` で落ちる。

- **添字 `i` は不可**: ファイルを1つ消すと添字がずれ、別の画像のウィジェット状態を引き継ぐ
- **ファイル名も不可**: 同名ファイルを2つ上げると衝突
- **`uploaded_file.file_id`** がアップロードごとに一意で、再実行をまたいでも変わらない

### 3-5. 描画順序と `st.rerun()`

Streamlit は実行しながら上から順に描画する。「選択中の食材」一覧を追加ボタンより**上**に置くと、追加ボタンを押しても一覧は既に古い内容で描画済みになる。

症状は「**追加を押しても何も起きない。別の操作をすると急に現れる**」。対策は追加直後に `st.rerun()` を呼ぶこと。

また、削除処理でループ中のリストを `remove()` しているのは、**直後の `st.rerun()` が実行を打ち切るから安全**。この `rerun()` を消すと本物のバグになる。

### 3-6. `use_container_width` は非推奨

`st.image(..., use_container_width=True)` は非推奨になり、警告が出る。`width="stretch"` に置き換える。

（さらに古い `use_column_width` は Streamlit 1.61 で完全に削除済み。画像アップロード時に `TypeError` で落ちる）

## 4. 環境・運用

### 4-1. `pip freeze` で requirements.txt を作ってはいけなかった

開発に使っていたのは個人用の共有 venv（`~/venv`、160パッケージ / 2.9GB）で、TensorFlow・Keras・Optuna・Google API クライアントなど本プロジェクトと無関係なものが大量に入っていた。

そのまま `pip freeze > requirements.txt` すると **TensorFlow 入りの160行のファイル**ができ、受け取った側の環境構築が失敗する。**直接使うパッケージだけを手書きした。**

### 4-2. `torch` はバージョンを固定しない

Windows と macOS(ARM) で配布ビルドが異なり、固定すると入らないケースがある。他のパッケージは固定、`torch` / `torchvision` のみ指定なしにしている。**チームメンバーが `pip install -r requirements.txt` で詰まったら、まずこの行を疑う。**

### 4-3. 手書きの requirements.txt は自動更新されない

`pip install` しても `requirements.txt` は変わらない。**新しいライブラリを入れたら必ず1行追記する。** 忘れると「自分のPCでは動くのに他の人の環境では ModuleNotFoundError」になる。
